# Non-collapse traceability

**Informative / Non-Normative.** For each of the seventeen non-collapse rules in Section 7.1 of `docs/specs/KEE-Specification-v0.11.0.md`, this page names what demonstrates it: the shape constraint that checks what can be checked structurally, the published data it runs over, and the executable test that shows a consumer's output moving when the owning dimension moves and staying put when the neighbouring one does. The identifiers `NC-01` through `NC-17` are the naming surface `normative-api/v0.11.0.json` publishes as `nonCollapseRuleIdentifiers`; they add no obligation (Section 7.1).

Section 18.5, whose text the specification carries in its informative annex (Section A.4), requires the release suite to "demonstrate changed consumer outcomes when the independently governed input changes, over repository fixtures, shapes, or tooling output, rather than merely searching documentation for phrases". A shape constraint on its own is not that: a shape can require a dimension to be present and can refuse a value that belongs to another axis, but it cannot show a consumer reading one dimension and ignoring the other. That is what the tests do. So the test column is the behavioural evidence Section 18.5 counts, and the shape and data columns are the structural half a reader can reproduce from the published files alone.

## How to read the table

- **Shape evidence** names a shape in `shacl/` and the constraint in it that carries the distinction. Every shape path resolves in this repository. Composition and the severity rule are in `shacl/README.md`.
- **Published data** names the example in `examples/` or the fixture in `fixtures/` the shape runs over. A fixture under `fixtures/invalid/` fails for the named reason; `fixtures/README.md` lists them.
- **Consumer-side test** names a test function in the working repository that maintains the specification. The working repository's `tests/` directory is not published, so the names are given as `module.py::function` without a path; they are not links. The functions read the published examples and the reference implementation's consumer functions, mutate a dimension in memory, and assert on the governed output.
- **Status** is `demonstrated` or `not demonstrable`, as Section 18.5 and the API manifest's `nonCollapseBehaviouralCoverage` field state it.

`docs/worked-example.md` follows one artifact through six of the examples and shows several of these distinctions with the validator's output pasted in.

## The two rules nothing demonstrates

Section 18.5, carried in full in the informative annex (Section A.4), on this point:

> **NC-03 (authority vs. responsibility) and NC-06 (confidence vs. trust) are not demonstrable at this baseline, and the reason is representational rather than epistemic.** A non-collapse rule can be demonstrated only where both of its sides are represented, as Section 7.1's own preamble scopes them. KEE represents authority and it represents confidence. It represents neither accountability as a surface distinct from authority, nor trust as a surface distinct from confidence. No shape, concept scheme, vocabulary document or example carries one. The obstacle is an absent vocabulary, not a judgment a consumer would have to make, and it lifts if and only if such a surface is introduced — which is a Section 4.2 admission question, not a testing question.

The one test listed against NC-03 and NC-06 does not demonstrate either rule. It searches the shape graphs, schemas, vocabulary and examples for an accountability or trust term and fails if one appears, so that the day a surface is introduced the declaration above is revisited rather than silently outlived. Introducing such a surface to reach seventeen of seventeen would be the wrong way round: the admission test in Section 4.2 comes first.

## Reconciliation with "fifteen of seventeen"

Three places state the coverage, and they agree:

| Where | What it says |
|---|---|
| `docs/specs/KEE-Specification-v0.11.0.md`, Section 18.5, carried in the informative annex, Section A.4 | "Behavioural coverage of the seventeen rules at this baseline is **fifteen of seventeen**. NC-01, NC-02, NC-04, NC-05, NC-07 through NC-17 are demonstrated." |
| `normative-api/v0.11.0.json`, `nonCollapseBehaviouralCoverage` | `demonstrated: 15`, `total: 17`, `notDemonstrable: ["NC-03", "NC-06"]` |
| this page | fifteen rows `demonstrated`, two `not demonstrable`, the same two |

The table has fifteen rules with at least one consumer-side test, and those fifteen are exactly the ones Section 18.5 lists. The working repository keeps this page in step with a machine-readable index of the same rows (`non-collapse-evidence.json`, beside the API manifest); a test there fails if a rule in the manifest has no named test or shape, if a named test function or shape does not exist, or if this page omits an identifier, test or shape the index lists.

Reconciling the claim against the evidence turned up the following, none of which changes the count:

1. **The identifiers were not in the tests.** A review of the repository observed that the `NC-` identifiers appeared in test code only for NC-01, NC-02, NC-03, NC-06 and NC-17, and then in tests about the API manifest and a fixture rather than in the behavioural tests, so a reader could not get from a rule to its evidence without this page. Each of the behavioural tests named above now states in its docstring which rule it demonstrates. No test's behaviour changed.
2. **The evidence for NC-12 is of a different kind.** The other fourteen demonstrated rules each have a test that mutates the neighbouring dimension and then the owning one over a published example. NC-12 is demonstrated by the reporting instead: a Draft profile's structural pass is reported with no normative effect, and a file that conforms only under the severity rule is reported as doing so. That is a changed tooling outcome on a governed input, which Section 18.5 admits, but it is not the two-mutation pattern.
3. **NC-14 cannot be reproduced from the published surface.** Its two sides are a decision record's own status and a published specification's text. The decision records are not published, so the test runs only in the working repository. The rule is demonstrated; it is the only one whose data a public reader cannot inspect.
4. **No invalid fixture exists for the authority basis.** The shape message "authority-basis evidence separately from provenance" is the structural statement of NC-02, and `docs/worked-example.md` shows it refusing a record whose `kee:authorityEvidence` has been removed, but there is no file under `fixtures/invalid/` pinning that result the way the other required constraints are pinned. The test column carries NC-02 regardless.
5. **An earlier evidence index exists in the working repository** for the 0.9.0 candidate. It binds the same fifteen rules to tests and the same two to a representation-gap review, so its count agrees, but it cites the historical baseline's Section 7.1 and names only test modules for its shape evidence. The index beside the current API manifest supersedes it for v0.11.0; the earlier one is retained as it was.
